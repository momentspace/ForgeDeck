# ADR 0003: Deckは根拠を持つ決定的なルールで作る

状態: 設計決定。実APIのフィールド対応は実装時に検証する。

## 決定

初期DeckにLLMを使わない。取得したGitHubの状態とユーザーの明示指定で分類する。カードには根拠と最終取得時刻、未確認の状態を表示する。通知の件数をIssue数と誤認させない。

分類の優先順位は、解消すべき自分の作業、確認済みマージ候補、待ち。複数理由を隠さず詳細に表示する。PR作者自身によるレビュー承認を許さない。コミットが変わった場合、古いレビューとチェックの再評価が必要。

「マージ候補」はマージ可能という保証ではない。実送信前に必須チェック・レビュー・ルール・権限・競合・head SHAを再取得し、条件変更時は中断する。mergeabilityが不明なら成功扱いにしない。検索結果は取得上限とページングを表示する。

待ちIssueは手動指定を基本にする。コメントの順番だけで相手から返事が必要と推定しない。関連Issue / PRは明示的な参照に限定し、タイトルの類似性で生成しない。

## サンプルとの違い

プロトタイプは各項目に架空の分類を持たせ、操作による移動を体験する。実GitHubのルールを網羅したエンジンではない。実装ではPure Kotlinの分類関数、取得範囲とルール根拠のモデル、未知の状態のテストを作る。

## 主なケース

レビュー依頼済み／取消し、CI failed／pending／unknown、draft PR、自己PR、更新後の古い承認、競合不明、権限なし、必須チェックと任意チェックの違い、Issueが複数PRと関連、PRに関連Issueなし、ページング途中、部分取得失敗、手動待ち解除。
